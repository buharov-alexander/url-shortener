# URL Shortener
[![CI](https://github.com/buharov-alexander/url-shortener/actions/workflows/ci.yml/badge.svg)](https://github.com/buharov-alexander/url-shortener/actions/workflows/ci.yml)

[Russian version](README.ru.md)

A service for shortening long URLs.

## Requirements
### Functional requirements
- Users can create short URLs from long URLs.
  - Short URLs must be unique.
  - Short URLs must be short (maximum length 11 characters).
- Users can be redirected from a short URL to the corresponding long URL.

### Non-functional requirements
- 200 million new URLs per month, read/write ratio 100:1.
  - Write QPS: ~76
  - Read QPS: ~7600
- Store links for 5 years, average size per link 500 bytes.
  - Storage: ~6 TB

## Requirements analysis
- Uniqueness of short URLs: requires either global coordination (centralized store) or an algorithm for generating unique identifiers. Global coordination can become a scaling bottleneck, so using an ID generation algorithm (Snowflake ID) is preferable.
- Maximum short URL length 11: with Base62 this is 62^11 ≈ 65 bits, enough to encode a 64-bit ID generated by Snowflake. If the max length were smaller (7–8 chars), we'd need centralized storage or a more complex ID compression scheme.
- Read QPS ~7600: this average (1k–10k) requires a load balancer and scalable storage.
- Storage ~6 TB: for >5 TB, a NoSQL datastore is preferable to avoid complex sharding in an RDBMS.

## Solution
- Generate a unique code for each URL:
  - First generate a unique 64-bit numeric ID using the Snowflake algorithm:
    - 41 bits for timestamp (ms) with a custom epoch. 41 bits provide ~69 years; epoch set to 2021-01-01 (usable until ~2090).
    - 10 bits for node ID (up to 1024 nodes).
    - 12 bits for sequence number (up to 4096 IDs per node per ms).
  - Encode the ID in Base62 to obtain a short string.
    - Resulting string is up to 11 characters long using [0-9a-zA-Z].
- Store mapping from short code to long URL in a database.
- On short URL request, extract code, look up long URL, and redirect with HTTP 301 (Permanent Redirect) so browsers and search engines cache redirects and reduce load.

### Architecture
- Add a Load Balancer (Nginx) in front of the service for traffic distribution.
- Store links in a NoSQL database (Cassandra) for scalability and high availability.

### Build and run
To build the service run the `build.sh` script in the project root. This builds required Docker images:
```
./build.sh
```
To run the service use Docker Compose:
```
docker compose up --scale app-service=2
```
This starts the service with 2 instances of the application to handle requests.

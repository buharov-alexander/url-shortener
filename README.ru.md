# URL Shortener
[![CI](https://github.com/buharov-alexander/url-shortener/actions/workflows/ci.yml/badge.svg)](https://github.com/buharov-alexander/url-shortener/actions/workflows/ci.yml)

[English version](README.md)

Сервис для сокращения длинных URL-адресов.

## Требования
### Функциональные требования
- Пользователи могут создавать короткие URL-адреса из длинных URL-адресов.
	- Короткие URL-адреса должны быть уникальными.
	- Короткие URL-адреса должны быть короткими (максимальная длина 11 символов).
- Пользователи могут перенаправляться по коротким URL-адресам на соответствующие длинные URL-адреса.
### Нефункциональные требования
- 200 миллионов новых URL в месяц, соотношение чтения/записи 100:1.
	- Write QPS: ~76
	- Read QPS: ~7600
- хранить ссылки в течение 5 лет, одна ссылка занимает в среднем 500 байт.
	- Хранение: ~6 ТБ

## Анализ требований
- Уникальность коротких URL-адресов: нужна либо глобальная координация (централизованное хранилище), либо алгоритм генерации уникальных идентификаторов. Глобальная координация может стать узким местом при масштабировании, так что предпочтительнее использовать алгоритм генерации уникальных идентификаторов (Snowflake ID).
- Максимальная длина коротких URL-адресов 11 символов: при использовании Base62 это 62^11 ~ 65 бит, что достаточно для хранения 64-битного идентификатора сгененерированного с помощью Snowflake ID. Если бы максимальная длинна была меньше (7-8 символов) пришлось бы либо использовать центролизованное хранилище, либо усложнять алгоритм генерации идентификаторов, чтобы сжать их в меньший размер.
- Read QPS ~7600: это среднее значение (1к - 10k) и для обработки запросов потребуется Load Balancer и масштабируемое хранилище.
- Хранение ~6 ТБ: это среднее значение (> 5 ТБ) для хранения такого объема данных лучше использовать noSQL. Иначе придется использовать шардирование в реляционной базе данных, что усложнит архитектуру.

## Решение
- Для URL генерируем уникальный код
	- Сперва генерируем уникальный 64-битный числовой идентификатор с помощью алгоритма Snowflake ID.
		- 41 бита для временной метки (в миллисекундах) с пользовательским эпохальным временем. 41 бит позволяют работать в течение примерно 69 лет. Эпохальное время установлено на 1 января 2021 года, это позволит использовать идентификаторы до 2090 года.
		- 10 бит для идентификатора узла (до 1024 узлов).
		- 12 бит для последовательного номера (до 4096 ID на узел в миллисекунду).
	- Затем кодируем идентификатор в Base62 для получения короткой строки.
		- В результате получается строка длиной до 11 символов, состоящая из цифр (0-9), строчных (a-z) и заглавных букв (A-Z).
- Сохраняем соответствие между уникальным кодом и длинным URL в базе данных.
- При получении короткого URL извлекаем код, ищем соответствующий длинный URL в базе данных и перенаправляем пользователя. Используем HTTP 301 (Permanent Redirect), чтобы браузеры и поисковые системы кэшировали перенаправления и уменьшали нагрузку на сервис.

### Архитектура
- Добавляем Load Balancer (Nginx) перед сервисом для распределения нагрузки.
- Хранение ссылок осуществляется в базе данных noSQL (Cassandra), что обеспечивает масштабируемость и высокую доступность.

### Сборка и запуск
Для сборки сервиса запустите скрипт `build.sh` в корневой директории проекта. Это соберет все необходимые Docker-образы.
```
./build.sh
```
Для запуска сервиса используйте Docker Compose:
```
docker compose up --scale app-service=2
```
Это запустит сервис с 2 экземплярами приложения для обработки запросов.
